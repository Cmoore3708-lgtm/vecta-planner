# Review stabilisation release — 15 October 2026

This batch follows access-protection PR #205. It is a preparation and verification
checkpoint, not a claim that the live system has been fixed.

## Changes in this batch

- Fleet saves compare the cloud revision and merge independent edits by stable
  record ID and field. Competing changes to one field are rejected visibly;
  pending/conflicting local work is retained rather than overwritten by refresh.
  A persisted confirmed baseline supports reconnection after offline edits.
  The nightly updater and MOT-authority writes use the same conditional-save path.
- Cloud SDK requests require a fresh network response. Last-known viewing remains
  available, with stale provenance on worker fallback responses. Health probes
  cannot return invented success or cached job rows. No financial reconciliation
  may use a successful-looking stale SDK response.
- Invoice lookup uses explicit links and performs no reconciliation writes,
  automatic completion or registration/date inference.
- Customer approval decisions lock the request and update its job in one
  transaction; repeat decisions return an idempotent receipt and conflicting
  decisions return 409. Only the server may call the function.
- Returning-customer lookup exposes autofill for the requested vehicle, without
  job history, notes or other owned vehicles. Empty/nonnumeric phone matching is
  rejected. The nightly route fails closed when its cron secret is absent.
- Regression discovery includes .test.js, .test.mjs and .test.cjs automatically.

## Added booking and backup work

Availability and public submission use the same database booking engine. The
engine applies Europe/London dates, two full Monday–Friday working days of notice,
nine calendar days for any request including MOT, closed Monday/weekend online
booking, resulting-load limits (75% Tue–Thu; 50% Friday), time off and pending
reservations on every day. Friday finishes at 14:30. Requests marked Contacted
continue reserving capacity; decline/archive/delete releases it. Reservations
remain until a workshop decision; there is no automatic expiry that silently
frees a customer's requested slot.

An advisory transaction lock serialises admissions per date. The selected time
and calculated duration are saved on the request. Explicit acceptance creates
new reserved jobs at that time/duration with Alfie and links the request's job ID.
Legacy requests without reservation metadata retain manual allocation. Atomic
cross-device manager acceptance and manual planner overrides are still separate
verification concerns; this change does not forbid a manager from moving jobs.

Both public booking screens now describe requests honestly, require registration
alongside manual vehicle details, resolve the vehicle placeholder, use Oil &
Filter Change terminology, and render before optional copy loads. The main API
validates work types and bounded inputs; the website proxy no longer implements
a competing rolling-48-hour rule. Old confirmation-copy fields cannot turn a
pending receipt into an accepted booking claim.

The backup uses one STABLE database function to export every current public
workshop table and the financial revision audit from one read snapshot. It
includes invoice links, published copy/history, reminder audit and subscriptions
when present. Missing required schema or any read error fails the whole export.
Counts, inventory, total and SHA-256 are checked. Responses stream in chunks;
production settings alone measured 9,915,382 JSON bytes during this work, larger
than Vercel's 4.5 MB buffered-response ceiling. No real data was downloaded to
measure that size.

The Windows runner validates counts and SHA-256 before replacing an old backup
or applying retention. It has not been executed on the actual workshop PC in
this environment. `scripts/validate-workshop-backup.mjs` provides an independent
portable verifier. Backups remain sensitive data; encrypted off-device retention,
the PC scheduled task, schema/functions/policies, Auth, Storage, hosting secrets
and the separate production-dependent relay project still need independent
recovery coverage. This is not a complete disaster-recovery backup.

### Additional verification

The database scenario files in `tests/database` passed in isolated Test. Booking
assertions cover the reproduced load defect, exact-capacity acceptance, pending
and contacted reservations, stale-time rejection, Friday time off/finish, weekend
and UK daylight-saving/lead-time boundaries. A real two-transaction race for the
same time admitted one request and rejected the other. The single committed
synthetic race fixture is marked Deleted in Test; ordinary scenario writes were
rolled back. No customer notifications or supplier calls were made.

The backup test restored every exported table into temporary tables and compared
every restored row, table count and total with the snapshot. Temporary restores
were rolled back. This proves data roundtrip against the existing Test schema;
it does not recreate a fresh database or prove recovery of production-only audit
schema. Service-role execution, unrelated authenticated denial and authorised
workshop booking access were checked. Tests also exercise streamed exports over
4.5 MB with backpressure, Unicode and escaped JSON, plus corruption/missing-table
failures. The availability database query took about 64 ms in Test; this is not
a claimed live customer latency or guaranteed speedup.
