# Review stabilisation release — 15 October 2026

This batch follows access-protection PR #205. It is a preparation and verification
checkpoint, not a claim that the live system has been fixed.

## Changes in this batch

- Fleet saves compare the cloud revision and merge independent edits by stable
  record ID and field. Competing changes to one field are rejected visibly;
  pending/conflicting local work is retained rather than overwritten by refresh.
  A persisted confirmed baseline supports reconnection after offline edits.
  The nightly updater and MOT-authority writes use the same conditional-save path.
- Cloud SDK requests require a fresh network response. Last-known viewing remains
  available, with stale provenance on worker fallback responses. Health probes
  cannot return invented success or cached job rows. No financial reconciliation
  may use a successful-looking stale SDK response.
- Invoice lookup uses explicit links and performs no reconciliation writes,
  automatic completion or registration/date inference.
- Customer approval decisions lock the request and update its job in one
  transaction; repeat decisions return an idempotent receipt and conflicting
  decisions return 409. Only the server may call the function.
- Returning-customer lookup exposes autofill for the requested vehicle, without
  job history, notes or other owned vehicles. Empty/nonnumeric phone matching is
  rejected. The nightly route fails closed when its cron secret is absent.
- Regression discovery includes .test.js, .test.mjs and .test.cjs automatically.

local edit and reports failed sync. Do not clear browser data to dismiss it.
Per-record database tables and smaller payloads remain a later migration: the
current change prevents blind overwrite but still transfers a fleet snapshot.

## Verification evidence

Targeted executable tests cover independent PC/iPad edits, cleared fields,
concurrent additions/deletions, same-field rejection, compare-and-swap retry,
read-only invoice lookup, stale viewing versus fresh reconciliation, denied-auth
fallback and customer-history response minimisation.

The isolated Test database accepted the approval migration. Transactional tests
verified first decision, duplicate retry, competing-decision rejection and
rollback of the job update after a forced approval-write failure. Test data and
the temporary failure constraint were rolled back. Anon and normal authenticated
roles cannot execute the decision function; service_role can.

A real Supabase CORS preflight accepts the fresh-required header. No customer
messages, live invoices or supplier lookup requests were generated by these tests.
